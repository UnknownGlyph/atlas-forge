## 1. 项目定位

一款**原生桌面地图创作与可视化软件**，用于现实世界地图、架空历史、虚构国家、幻想世界、历史地理研究和统计数据可视化。

核心要求（来自需求方）：
- 原生桌面，不使用 Electron/WebView 作为核心渲染载体；完全离线可用。
- 以**矢量几何**为核心，而不是图片。
- 二维地图（多投影）、三维球体、数据专题地图**共享同一份底层数据**。
- 相邻国家共享边界，不能出现缝隙、重叠或编辑不同步。
- 高性能（GPU 渲染、增量更新、LOD、空间索引），并且要有**真实基准**，而不是口头宣称。
- 第一个版本就要有一条真实可用的完整工作流：
  **创建地图 → 绘制国家 → 编辑边界 → 保存 → 重新打开 → 三维球体 → 修改统计数据 → 导出**。

## 2. 技术栈与选型理由

| 层 | 选择 | 版本 |
|---|---|---|
| 语言 | Rust | 1.99.1（MSVC 工具链） |
| GPU | wgpu（Windows 上走 DX12/Vulkan） | 30 |
| UI | egui / eframe（立即模式） | 0.37 |
| 持久化数据结构 | imbl（结构共享的 OrdMap） | 7 |
| 三角化 | earcutr | 0.5 |
| 序列化 | serde + rmp-serde（MessagePack）+ lz4_flex | — |
| 导出光栅化 | tiny-skia + ab_glyph（中文字体取系统 msyh.ttc） | — |
| 文件对话框 | rfd | 0.17 |

**比较过的方案**：
- C++/Qt 6：控件丰富、GIS 生态（GEOS/PROJ/GDAL）原生，但本机未安装 Qt，构建和依赖成本高，也有许可问题。
- C#/Avalonia：开发快，但 GPU 绘制要自己写一层，存在 GC 停顿。
- Rust + wgpu + egui（**已选**）：只用 cargo 就能构建，内存安全，写测试和基准方便。项目最难的部分是数据结构、算法正确性和 GPU 渲染，而不是表单控件。

**已知代价**：egui 是立即模式 UI，复杂的停靠窗口、大表格、富文本不如 Qt。UI 层只依赖 `map_core` 的公开 API，将来可以替换。

**环境备注**：本机 Visual Studio 没有在 vswhere 中注册，rustc 找不到 MSVC 链接器，所以构建统一通过 `tools/cargo-msvc.cmd`（先加载 `vcvars64.bat`）。

## 4. 核心设计决策（这些在早期定下，后期很难再改）

### 4.1 共享边界的平面拓扑（ADR-1）

```
Node  { pos: LonLat }
Edge  { a: NodeId, b: NodeId, pts: Vec<LonLat>, left: FaceId, right: FaceId, bbox }
Face  { kind: Land|Water, outer: Ring, holes: Vec<Ring>, rev, bbox }
Ring  = Vec<ArcRef { edge, rev: bool }>
```

- **不变量**：面位于自己每条环的左侧（外环逆时针、洞顺时针）。环里正向引用一条边，意味着 `edge.left == 该面`；反向引用则 `edge.right == 该面`。每条边恰好被正向、反向各引用一次。`Topology::validate()` 检查全部不变量，测试中每次编辑后都会调用。
- `FaceId(0)` 是"世界海洋"，没有外环，顶层陆地的海岸线是它的洞。
- **国家不是几何**：国家是 `Entity`，通过 `owner: FaceId → EntityId` 拥有若干面。
  - 合并国家、割让领土 = 改归属，几何不变；飞地、多块领土天然支持。
  - 国界 = 两侧归属不同的边；海岸线 = 陆地与水体之间的边；内部边界 = 同一国家内部的边。三者来自同一组边，所以不可能出现缝隙或重叠。
- 已实现的拓扑编辑操作：
  - `add_ring_face`：在某个面内画闭合环，生成岛或湖；被新环包住的已有环自动成为它的洞。
  - `split_face`：从边界画到边界，一个面切成两个。这是画国界、行政区的主要方式。
  - `move_vertex` / `insert_vertex` / `delete_vertex`：共享边界上的点只存一份；会检查是否产生相交、岛/湖是否跑出所在面。
  - `merge_faces`：删除两个面之间的共享边。
  - `split_edge`、`assemble_rings`（把有向边串成闭合环）、`first_hit`（射线与边界的第一个交点）、吸附查询（最近顶点、最近边上点）。

### 4.2 坐标与几何语义（ADR-2）

- 存储：经纬度 f64（度），经度规范到 [-180, 180)。
- **边的定义**：相邻两点之间取经度差小于 180° 的方向，在经纬度平面上是直线（与 GeoJSON 的常见做法一致），因此平面算法（耳切三角化、相交、点在多边形内）可以直接使用。
- **面积**：对"经纬度直线边"做球面上的精确积分 `A = R² ∮ −sin φ dλ`。与解析解比较，误差小于 1e-12。星球半径可配置。
- **包含极点的环**：展开后经度绕行 ±360°，用 lat = ±90 的伪边闭合成普通平面多边形。渲染已支持，绘制工具目前不允许画这种环。
- **取舍**：没有采用 S2 那种"大圆边"语义。好处是算法简单可靠、兼容 GeoJSON；代价是长边在球面上既不是大圆也不是恒向线（恒向线对应墨卡托上的直线）。二维绘制时会按屏幕直线自动补点，所以实际的边很短，但误差上限尚未量化。

### 4.3 渲染：投影在 GPU 上完成（ADR-5）

- 每个面的处理流程：展开环 → 耳切三角化 → 细分到最长边不超过 2°（用于贴合球面和投影曲率）→ 沿 ±180°（相对中央经线）精确切割。输出的顶点只有 `(lon, lat, face_slot)`，与投影无关。
- 顶点着色器负责投影：等距圆柱、墨卡托、米勒、Equal Earth，或者三维球面。**切换投影或在二维/三维之间切换都不需要重建网格**。
- 颜色放在单独的 storage buffer 里，每个面一个颜色。换专题图只上传颜色，不动几何。
- 边界线：每条线段是一个实例，在顶点着色器中按屏幕像素宽度扩成四边形，所以任意缩放下线宽恒定，带抗锯齿。
- 球体：先画海洋网格，再画同一份陆地网格；片元着色器里做地平线剔除，不需要深度缓冲。
- **增量更新**：每个面有一个全局唯一、单调递增的几何版本号 `rev`，网格缓存以 `(面, rev)` 为键，只重新三角化变化的面。边线和叠加层用 imbl 的 `ptr_eq` 判断是否需要重建。
- 已知简化：三角形以"三角形汤"形式存储，顶点没有去重（内存约 ×3）；整个场景只有一个顶点缓冲，没有分块。

### 4.4 属性与统计（ADR-3）

```
FieldDef { key, name, kind: Number|Text|Bool|Category, unit, expr: Option<String> }
Entity   { kind: Country|Region|City, code(稳定外部ID), name, short, color, parent, capital, pos, note }
values   : (EntityId, FieldId) → Series { base: Option<Value>, by_year: BTreeMap<i32, Value> }
```

- 字段完全由用户自定义；唯一的内置字段是 `area_km2`（由几何计算）。
- **时间维从第一版就在数据结构里**：取值规则是"不晚于当前年份的最近一个值，否则用基础值"。
- 派生指标是一个小型表达式语言：`+ - * / ( )`，函数 `min max abs sqrt ln log10 pow`，可以引用其他字段的键。例如 `population / area_km2`。缺失值会向上传播，除以 0 视为缺失。
- CSV 导入按 `code` 关联实体（找不到 `code` 列时用 `name`）；可选 `year` 列写入时间序列；未知列自动建字段并推断类型。

### 4.5 撤销/重做（ADR-4）

`Document` 的各张表都使用 `imbl::OrdMap`（结构共享的持久化 B 树），克隆是 O(1)。撤销栈直接保存修改前的整个文档。
- 好处：任何编辑都自动可撤销，不需要为每个拓扑操作手写逆操作（这类软件最常见的 bug 来源）；编辑失败时也能精确回滚。
- 交互式编辑（拖动顶点、领土画笔连续涂抹）在开始时记录一次快照，结束时整体作为一步撤销。
- `rev` 计数器刻意放在文档之外（进程级全局），保证撤销后也不会重复使用版本号，网格缓存因此不会出错。

### 4.6 工程文件（ADR-6）

`.atlas` = 魔数 `ATLASMAP` + 格式版本号（u32）+ LZ4 压缩的 MessagePack（按字段名序列化）。
- 保存时先写临时文件，再原子替换。
- 读取时校验版本号，并保留迁移钩子；新增字段用 serde 默认值，保证向后兼容。
- 不支持增量保存。未来可能迁移到 SQLite 容器。

## 5. 已完成功能

### 5.1 编辑工具（桌面程序）
选择/浏览、绘制陆地、绘制湖泊、切分/画边界、编辑顶点（拖动、在边上插入、右键删除）、领土画笔（左键分配、右键取消归属）、合并相邻面、添加城市、绘制河流。所有工具在二维视图和三维球体中都可以使用（两种视图都先把指针换算成经纬度）。快捷键：V L K S E B M C R，Ctrl+Z / Ctrl+Y / Ctrl+S / Ctrl+O。

### 5.2 视图
- 二维地图：4 种投影，可调中央经线，滚轮以光标为中心缩放，右键/中键平移，可选经纬网。
- 三维球体：旋转、缩放、光照、地平线剔除。
- 布局：仅二维、仅三维、二维与三维分屏。
- 叠加层：国家名称（按面积排序、贪心避让）、城市点与名称、选中轮廓、悬停轮廓、绘制中的草稿线、吸附提示、顶点手柄。

### 5.3 面板
- 国家：列表（含面积）；名称、简称、编号、颜色、首都、备注；设为画笔、删除、合并到另一国家、把所选地块分离为新国家。
- 数据表：所有国家 × 所有字段，可直接编辑；可切换按年份查看和编辑。
- 字段：新建（含派生表达式）、删除。
- 专题图：政治地图 / 分级设色；指标、分级方法、分级数、5 种色带、缺失值颜色、图例预览。
- 样式/世界：各类颜色与线宽、是否显示标注和城市、星球半径、世界名称。

### 5.4 文件与交换
新建（空白世界或示例世界）、打开、保存、另存为；关闭窗口时提示未保存的修改。
- 导入：GeoJSON（简单导入）、CSV 属性。
- 导出：PNG、SVG、GeoJSON（按国家融合或按地块）、CSV。可设置尺寸、投影、范围（全图或当前视图）、标题、标注、图例、经纬网。

## 7. 已知限制与技术债

1. **新画的多边形不能与已有边界相交或接触**：没有布尔并集/裁剪，也不会自动吸附到已有边界上。
2. **GeoJSON 导入不识别共享边**：相邻国家的多边形会因为"接触"而被拒绝，所以现实世界的国界数据（如 Natural Earth）基本无法导入。
3. **相交检测和面查找是 O(N) 暴力遍历**，只有 bbox 预筛，没有 R 树。
4. **单一 GPU 顶点缓冲**，任何几何变化都要整体拼接一次；三角形顶点没有去重。
5. **国家标注锚点**在拓扑变化后对所有国家重新融合计算（拖动期间已跳过）。
6. **样式和专题图参数的修改不进入撤销栈**。
7. **包围极点的环**只能显示，不能用工具绘制；"删除节点（交汇点）"未实现。
8. **GPU 使用 f32 经纬度**（约 1 m 精度），极大比例尺下会抖动；尚未实现"相对视点中心"的坐标方案。
9. **egui 的限制**：没有原生停靠窗口；数据表在列很多时不够好用。
10. **归属还没有时间维**（属性值已有），所以历史版图时间轴还不能实现。
11. 所有计算都在 UI 线程同步执行，没有后台线程。

## 8. 后续路线（当前计划，欢迎调整）

- **P1 编辑体验**：吸附（顶点/边/角度）、框选、批量修改归属、弧段简化（Visvalingam）、清理度为 2 的多余节点、**GeoJSON 导入时建立共享拓扑**（TopoJSON 式识别共享弧）、底图图片导入与配准、河流/道路线要素编辑、新画多边形与已有陆地自动合并/裁剪。
- **P2 专题地图与数据**：自然断点（Jenks）、双变量配色、比例符号、点密度、筛选与对比视图、图例编辑器、配色模板、统计面板。
- **P3 时间与历史**：时间轴；归属随时间变化（`owner` 增加时间维度）；边界变化动画；包含极点区域的编辑。
- **P4 规模与性能**：R 树空间索引；按空间分块构建 GPU 缓冲；按缩放层级简化弧段（LOD）；后台线程三角化；相对视点中心坐标；SQLite 工程容器与增量保存；改进标注避让。
- **P5 扩展**：地形高度、山脉、海底地形；星球参数；三维导出（glTF）；插件系统（基于稳定 API 的脚本或 WASM）。

## 9. 希望重点评审的问题

1. **几何语义**：选择"经纬度直线边"而不是"大圆边"（S2 式）是否合理？对于以虚构世界为主、但也要导入真实数据的软件，这个决定未来会不会成为瓶颈？
2. **拓扑模型**：在"节点-边-面 + 国家只是面的归属"这个模型上，加入**行政层级**（国家 → 省 → 县）和**随时间变化的归属**，最合适的数据结构是什么？（例如：每个面在每个层级各有一个归属，还是一张按时间区间记录的归属表？）
3. **GeoJSON/Shapefile 导入建拓扑**：把现实数据（存在微小缝隙和重叠）转换成干净的共享边拓扑，推荐什么算法或开源实现（TopoJSON、GEOS、PostGIS topology、`geo` crate 的布尔运算等）？容差应该怎么处理？
4. **布尔运算**：新画的多边形与已有陆地自动合并或裁剪，在 Rust 里用 `geo` 的 BooleanOps、i_overlay，还是自己在拓扑上做弧段求交？各自的稳健性如何？
5. **撤销方案**：持久化数据结构的整文档快照，在百万顶点规模下还撑得住吗？是否应该提前换成"命令 + 补丁"模式？
6. **渲染**：下一步的优先顺序——空间分块缓冲、LOD 简化、索引网格、相对中心坐标——你会怎么排？二维地图是否应该改用 GPU 上的矢量瓦片式结构？
7. **UI 框架**：egui 在这个产品上的长期上限在哪里？是否值得早期就考虑换成 Slint、Iced，或者"Qt 外壳 + Rust 核心"？
8. **产品优先级**：以"架空历史 / 幻想世界创作者"为主要用户时，P1 到 P3 里最应该先做的三件事是什么？有没有遗漏的关键功能（例如程序化生成海岸线、文化/宗教/语言等多套"归属层"、地名自动生成）？
9. **工程文件**：MessagePack 整体快照与 SQLite（类似 GeoPackage）相比，在什么规模下应该切换？迁移的成本和风险如何？
10. **测试策略**：几何与拓扑代码，除了现有的单元测试和端到端测试，还应该加入哪些测试（例如基于属性的随机测试、模糊测试、与 GEOS 结果对比）？
